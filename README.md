# ELF Static & Dynamic Analyzer

Автоматизированный инструмент для комплексного статического и динамического анализа исполняемых файлов формата ELF. Проект направлен на восстановление графов вызовов (Call Graph) и графов потоков управления (CFG) с последующей верификацией достижимости функций через динамическую трассировку и фаззинг окружения.

---

## Цели и задачи исследования

**Основная цель:** Количественная и качественная оценка эффективности разработанного инструмента в сравнении с эталонными коммерческими и открытыми решениями (Ghidra, IDA Pro).

**Решенные задачи:**
1. **Формирование датасета:** Собран репрезентативный набор из 1000 бинарных файлов (системные утилиты Kali Linux и вредоносное ПО).
2. **Методология сравнения:** Настроен автоматизированный пайплайн для пакетного (headless/batch) извлечения графов из Ghidra и IDA Pro.
3. **Динамическая верификация:** Реализован сбор трасс выполнения с помощью Frida и GDB для формирования "истинных" (Ground Truth) графов.
4. **Сравнительный анализ:** Рассчитаны метрики Precision, Recall и F1-Measure для выявления сильных сторон и ограничений подхода.

---

## Архитектура и ключевые возможности

### 1. Статический анализ (LLVM IR)
- **Декомпиляция:** Использование `RetDec` для трансляции ELF-файлов и разделяемых библиотек в LLVM IR.
- **Парсинг IR:** Извлечение карт вызовов (Call Maps), глобальных переменных, косвенных регистров и логики функций.
- **Многоуровневые эвристики (5 уровней):**
  - *Level 1:* Адресное выравнивание (Address Alignment).
  - *Level 2:* Анализ потока данных аргументов (Arg Dataflow).
  - *Level 3:* Оценка сложности (Complexity).
  - *Level 4:* Стохастическое голосование (Stochastic Voting).
  - *Level 5:* Анализ ролей API libc (Libc Role / Jaccard similarity).
- **Разрешение релокаций:** Автоматический маппинг PLT/GOT записей на реальные символы через `pyelftools`.

### 2. Динамическая верификация (Frida & ENV Fuzzing)
- Автоматическая генерация Frida-хуков для целевых функций.
- **ENV Fuzzing:** Извлечение строк и переменных окружения (`getenv`, `strstr`) из LLVM IR и автоматический перебор их комбинаций для триггера скрытых веток выполнения.
- Сбор стека вызовов (Backtrace) в момент срабатывания хука.

### 3. Анализ библиотек и слияние графов
- Автоматическое определение топ-3 зависимых библиотек через `ldd`.
- Построение единого графа с цветовой дифференциацией: основной бинарник (голубой), библиотечные функции (зеленый) и функции-мосты (желтый).

## Быстрый старт

### 1. Формирование датасета
Скрипт автоматически находит все 64-битные ELF-файлы в `/usr/bin` и `/usr/sbin`, перемешивает их и отбирает ровно 1000 образцов.

```bash
#!/bin/bash
DATASET_DIR="./elf_dataset_1000"
mkdir -p "$DATASET_DIR"

find /usr/bin /usr/sbin -type f -executable 2>/dev/null | while read filepath; do
    if file "$filepath" | grep -q "ELF 64-bit"; then
        filename=$(basename "$filepath")
        cp "$filepath" "$DATASET_DIR/$filename" 2>/dev/null
    fi
done

ls -1 "$DATASET_DIR" | shuf | tail -n +1001 | while read f; do
    rm "$DATASET_DIR/$f"
done
```

### 2. Запуск разработанного анализатора

Скрипт `unified_analyzer.py` поддерживает автоматический и интерактивный режимы работы.

**Автоматический режим** (анализ бинарника + 3 библиотек + слияние графов):

```
python3 unified_analyzer.py /path/to/binary ./output_dir
```

*Результат:* `.ll` файлы кэшируются в `ll_files/`, итоговые графы сохраняются в формате `.dot` (для визуализации используйте `dot -Tpng graph.dot -o graph.png`).

**Интерактивный режим** (запуск без аргументов):

```
python3 unified_analyzer.py
```

Пользователю будет предложено вручную указать путь к целевому ELF-файлу. В этом режиме анализ ограничивается только основным бинарником, без автоматического разрешения зависимостей через `ldd`.

---

### 3. Получение эталонных данных (Baseline)

Для корректного сравнения результатов необходимо извлечь графы потоков управления и графы вызовов с помощью эталонных инструментов в пакетном (headless) режиме.

**Ghidra (Headless mode):**
Извлечение графа вызовов через PyGhidra API.

```
pyghidraRun ghidra_script.py /path/to/binary
# Результат сохраняется в /tmp/cfg/call_graph_<имя>.dot
```

**IDA Pro (Batch mode):**
Извлечение CFG на уровне базовых блоков с автоматическим анализом.

```
idat -A -S"ida_script.py ./output_dir" /path/to/binary
```

## Методология оценки

В качестве "Ground Truth" (истинных значений) выступают данные динамической трассировки, собранные с помощью Frida и GDB в двух режимах:

1. **`validation_traces`**: Фиксирует функции, выполненные строго в пределах адресного пространства основного бинарника (до перехода в GOT/PLT).
2. **`validation_full_traces`**: Фиксирует полный граф выполнения, включая все вызовы сторонних разделяемых библиотек (например, `libc.so.6`).

**Формулы метрик:**
- **Precision (Точность):** $P = \frac{TP}{TP + FP}$
- **Recall (Полнота):** $R = \frac{TP}{TP + FN}$
- **F1-Measure:** $F1 = 2 \times \frac{P \times R}{P + R}$

Где:
- **TP (True Positive)** — функция обнаружена инструментом и реально выполнялась согласно трассе.
- **FP (False Positive)** — функция обнаружена инструментом, но не выполнялась в трассе (артефакт эвристики).
- **FN (False Negative)** — функция выполнялась в трассе, но не была обнаружена инструментом.

### Итоговые результаты (усредненные по датасету)

**Таблица 4.1 – Метрики качества (validation_traces / только основной бинарник)**

| Инструмент | Precision | Recall | F1-Measure |
| :--- | :---: | :---: | :---: |
| IDA Pro | 0.479 | 0.581 | 0.485 |
| Ghidra | 0.787 | 0.584 | 0.661 |
| **Разработанный способ** | 0.011 | 0.520 | 0.021 |

**Таблица 4.2 – Метрики качества (validation_full_traces / бинарник + библиотеки)**

| Инструмент | Precision | Recall | F1-Measure |
| :--- | :---: | :---: | :---: |
| IDA Pro | 0.497 | 0.021 | 0.036 |
| Ghidra | 0.826 | 0.022 | 0.040 |
| **Разработанный способ** | 0.392 | 0.551 | 0.441 |

> **Вывод:** Разработанный инструмент демонстрирует преимущество в режиме `validation_full_traces`. Благодаря анализу LLVM IR, многоуровневым эвристикам и слиянию графов библиотек, инструмент обеспечивает высокую полноту (Recall 0.551) там, где классические дизассемблеры "теряют" контекст из-за динамического связывания и PLT/GOT переходов. Однако 0.441 мало для успешного результата.
